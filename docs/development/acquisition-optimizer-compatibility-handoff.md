# Acquisition and optimizer compatibility audit: handoff

## Scope and evidence

The audit inventory is generated by `scripts/audit_acquisition_optimizer_matrix.py`.
It covers registered model and acquisition metadata, dispatcher optimizer backends,
and separately listed specialized optimizer paths. The acquisition-by-optimizer
matrix distinguishes static metadata from explicitly scoped runtime tests.

The existing runtime evidence covers selected binary classification, regression,
and multiobjective acquisitions under their recorded test conditions. In particular,
the continuous q=1 evidence does not establish q>1, constrained, integer,
categorical, or mixed-variable runtime compatibility. A capability declaration is
not a runtime test. A `not_declared` status is not proof of mathematical
impossibility or evidence that a backend cannot be extended.

## Reproduce the inventory

From an installed development environment:

```bash
python scripts/audit_acquisition_optimizer_matrix.py --summary
python scripts/audit_acquisition_optimizer_matrix.py --output /tmp/bo-matrix.json
pytest tests/acquisition/test_acquisition_optimizer_inventory.py
ruff check scripts/audit_acquisition_optimizer_matrix.py tests/acquisition/test_acquisition_optimizer_inventory.py
ruff format --check scripts/audit_acquisition_optimizer_matrix.py tests/acquisition/test_acquisition_optimizer_inventory.py
```

The full JSON contains `acquisition_optimizer_static`,
`optimizer_variable_type_matrix`, `acquisition_variable_type_coverage`,
`variable_type_gap_queue`, and `gap_triage`. The summary reports aggregate
coverage and counts without conflating declared and verified support.

## Next implementation workflow

1. Select the acquisition, optimizer backend, variable type, and intended
   model, batch size, and constraint conditions.
2. Inspect the corresponding `acquisition_variable_type_coverage` entry and
   `gap_triage` group. Check whether the backend uses a dispatcher or
   specialized path.
3. If capability is declared but unverified, add a targeted runtime test for
   the intended combination. If it is not declared, review the backend contract
   and implementation before changing capability metadata. One-shot and other
   specialized paths require their own tests.
4. Record the test file and exact scope in the inventory only after the test
   passes. Do not promote a declared-only mixed capability to verified on the
   basis of a continuous test.
5. Run inventory contract tests, relevant runtime tests, Ruff check, and Ruff
   format check before opening a PR. Check CI after opening the PR.

## Audit completion boundary

The inventory, gap extraction, triage, and compact reporting workflow are in
place. This closes the *inventory and traceability* stage, not an exhaustive
runtime certification of every acquisition, model, variable type, optimizer,
batch size, and constraint combination. Remaining gaps are tracked work items,
not implicitly supported configurations.

Future feature work should use the existing matrix to select targeted changes.
A full audit restart is unnecessary unless the underlying registry or contract
architecture changes substantially.
